### R3 · 后端骨架

```
实现后端基础设施，编译必须通过：
- 配置全部来自环境变量，启动时集中校验、缺关键配置（如 JWT_SECRET）快速失败；
- 类型化错误类 + 全局异常处理器，客户端只看到 {success,data,error:{code,message},requestId}，绝不返回堆栈；
  结构化 JSON 日志携带 requestId，禁止记录密码/令牌；
- 请求 ID 过滤器、显式来源 CORS、/health 与 /ready、优雅停机；
- 认证：PBKDF2 加盐哈希、HS256 短时效 access token、服务端存储的 refresh token
  （httpOnly cookie + 轮换）、@RequireRole 注解 + 拦截器（员工访问 /api/console/** 必须 403）；
- 注册/登录的邮箱格式、长度 ≤200、密码 ≥8 且含字母与数字、重复邮箱、错误密码都要有明确英文提示。
完成后运行 mvn test 或至少 mvn -DskipTests package，贴出 BUILD SUCCESS。
```

### R4 · 菜单、搜索、选项、价格、缓存

```
实现菜单域，逐条对照评分点：
- GET /api/menu 服务端分页（默认 12/页，上限 48）、分类多选筛选、名称/描述关键词搜索；
  搜索必须参数化（JPA Specification），转义 % 和 _，关键词 ≤50 字符，禁止拼接 SQL；
- 菜品详情含 protein / allergens / spice level / 选项组（必选/可选/maxSelect/额外费用）；
  前端选择后价格实时更新；金额全链路整数分，落库 DECIMAL(10,2)，禁止浮点；
- 菜品数据、枚举、所有提示一律英文；
- 菜单热点数据做 TTL 缓存（默认 30s），说明命中/失效策略，所有写路径（下单、取消、后台改菜、
  改每日菜单、改偏好）主动 invalidate，并提供命中率观测端点；
- 选项组/选项用批量查询装配，禁止 N+1。
```

### R5 · 下单主链路（最高优先级）

```
这是最关键的一轮：下单不通，Tier 3 全部级联归零。先只做下单链路并端到端验证，不要做看板/AI。
1) 幂等：前端每次结算生成稳定 Idempotency-Key，后端 DB 唯一约束兜底；连续点击、并发重复请求
   只能产生一个订单；并发冲突要返回已存在的那个订单而不是报错；
2) 每单总份数 ≤5（不是品种数），前端按钮禁用并说明原因，后端同样校验；
3) 截单：Lunch 10:00 / Dinner 15:00；超时自动切换「当日 Dinner」，当日晚餐也截单则「次日 Lunch」，
   并把切换说明返回给前端；
4) 同日同餐次每人只能有一个有效订单（Pending/Confirmed），结算页按钮变 View Existing Order；
5) 服务端重新计算价格（绝不信任客户端传价），校验必选选项、上下架、是否在当日菜单；
6) 库存：原子条件 UPDATE `remaining_qty >= qty`，多员工并发不能超卖；提交时库存不足要明确告诉
   哪些菜品不足、各剩多少，整单回滚；取消仅允许 Pending 且恢复库存（不超过当日供应量）；
7) 订单成功页含订单号/配送日期/餐次/地址；我的订单可查看详情（选项、数量、小计、总价）。
完成后必须用 curl 实际下单两次（相同 Idempotency-Key），贴出两次返回相同的 orderNo，
再贴一次取消后的库存数值。不要只说「已实现」。
```

### R6 · 前端 SPA（P6+ 一次点名）

```
实现全英文 React SPA，逐条对照附录 A.1：
- 响应式：手机/电脑双端，960/640 断点，移动端底部导航，卡片网格自适应；
- 分页/性能：服务端分页 + 图片懒加载，50+ 菜品仍流畅；
- 防抖/节流：搜索 300ms 防抖、加入购物车 200ms 节流、提交按钮在请求中禁用；
- 价格精度：整数分计算与展示（¥22.50），输入金额用字符串解析；
- 输入校验：邮箱/地址 ≤200、搜索 ≤50、AI 输入 ≤500，客户端正则 + 服务端校验；
- API 客户端：Base URL 走环境变量，401 自动刷新并重试一次，4xx 不重试、5xx 最多重试 3 次，
  断网显示离线提示，后端错误映射成友好英文文案；
- 购物车：同菜品不同配置是不同条目，实时总价，达到 5 份禁用所有加号；
- 结算页：日期/餐次/地址（历史地址可选）、预算超支提示、已有订单切换按钮、订单成功页。
用 npm run build 验证并贴输出。
```
